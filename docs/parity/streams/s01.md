## Contract and limits

The legacy `inspection:"capability-matrix"` remains compatible. Its selected
rows gain `readiness: CapabilityStatus`: independent source, mount, callable
route, enrollment, enabled, ready and live-evidence observations. This first
publication is callable through that legacy route. The modular definition is
registered, but provider-schema exposure, host-port binding and runtime dispatch
await C01/C02. Once exposed, it calls the same inspection through the named host
port; registration alone is not modular callability. Module configuration defaults
on, with explicit disables preserved by the integrating runtime. Existing role,
scope, stop and admission fences remain unchanged.

The reader's optional fourth host-only argument selects `"direct"` (default) or
`"metadata"` presentation. Only capability-matrix rendering changes: direct
WhatsApp remains compact for its single-message limit, while the named worker
port can obtain complete K7 JSON with the original event intact. No model-selected
presentation field, source substitution, adapter splitting or new grants exist.

Current local observations expire after one minute. Missing, invalid, future and
expired evidence cannot establish current readiness; revisions come only from
the runtime's loaded release, never Git or a moving symlink. A positive local
metadata route is not process/provider health. External enrollment is unknown
unless separately observed; local interfaces with no separate account say so.
Live feature attestation remains explicitly unknown. No new attestation store,
automatic probing, poller, repair authority or retained personal data is added.

Missing/unknown prerequisites name their code, resolver and safe route. The
ledger identifies absent coding runtime/workspace, closed activation, missing
search credential, local KVM device access and unsafe browser PIN/intake
combination. A KVM metadata/access check never opens the device or starts a VM.
MCP enrollment/expired credentials resolve through the existing read-only
enrollment inspection and authenticated private Connections workflow. Companion
compatibility stays unknown without evidence; different SHAs alone are not a
mismatch. Explicit process/debug-site probes remain separate existing inspections.

The owner's 10 October correction limits the financial restriction to autonomous
purchases, orders, transfers and new financial commitments, including quota
purchases and wallet top-ups. Ordinary configured inference and tools, including
search and E2B, are permitted without billing-classification or no-charge
attestations. Unknown or metered billing is not a readiness prerequisite or a
reason to deny that ordinary use; permission does not assert that usage is free.
Configured availability, consent, permissions, privacy, provider quotas, rate
limits, bounded concurrency, cancellation and lifecycle safeguards remain.
New financial commitments require explicit owner authorization; account access
or a payment login is not that authorization. Shared metadata keys stay compatible,
and all four S01 prompt paths receive the corrected policy. Informational
`liveVerified: unknown` and real readiness prerequisites are unchanged. No billing
audit, spending database or adapter-enforcement claim is introduced.
