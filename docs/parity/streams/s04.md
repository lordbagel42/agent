## Current owner policy supersedes the original model-budget proposal

The owner's 10 October 2026 clarification separates inference from new spending:

- Existing authorized subscription/included inference has no artificial token
  quota or model-use USD cap, including useful background inference. Missing
  prices do not block that included use. Actual provider rate limits, concurrency,
  cancellation, recovery fences and foreground priority remain. No idle busy loop.
- Do not spend owner funds now, including through Stripe Link. A future
  owner-funded transaction requires a changed policy, Stripe Link and fresh
  explicit authorization. A login, credential, credit balance or tool grant is
  not approval. No alternate payment route, purchase, top-up, paid fallback,
  phone charge or paid tool/compute provisioning is authorized.
- Separately metered API billing is not assumed free/included. Resolve the
  ambiguity before incurring a charge; a protocol or model name is not billing
  evidence. Possible future June-earned funds authorize no earning or spending
  now, and owner funds/credits cannot be relabeled as earnings.

No numeric caps, prices, provider enrollment, new dependency or durable schema
were approved. The proposed private `budgets.sqlite` remains unapproved and is
not created. This does not block a static no-spend denial policy.

## Contract and actual callable slice

`src/budgets/policy.ts` exports synchronous host-only
`spendingAdmission(SpendingClass): SpendingAdmission`. Exact classifications are
`included-inference`, `verified-no-charge`, `owner-funded`, and `unknown`.
Only the first two pass the money-policy check. Owner-funded spending returns
`owner_spending_prohibited`; unknown or unrecognized classifications return
`billing_unverified`. Passing this check grants no source/account/action access.
The host must establish classification for the exact provider/account/action;
never copy it from model arguments, remote tool descriptions or `readOnlyHint`.

The existing `analytics:{"days":1|7|30}` action reads `UsageLedger.report` and
includes budget readiness. It reports only allowlisted observed protocol labels
and aggregate counters, never account/model identifiers or new private bodies.
Completion, failure, token counts and model liveness cannot classify a charge.
Amounts, reservations and remaining allowance stay unavailable—not zero.

Interaction delegates task-relevant inspection; authorized execution reads the
report. Event decisions require an actual analytics grant. Notification-only
and completion turns receive knowledge but no action. Availability alone is not
an instruction to poll analytics. No new scheduler, provider call or persistence
is introduced by inspection.

Publication of this helper is **not global host enforcement**. Each actual
provider/tool owner must integrate and verify its pre-dispatch check. The report
explicitly does not attest F001/F002 release evidence or full F013 completion.

## Verification and delivery limits

Disposable local checks exercise the real OpenAI/Anthropic JSON adapter paths
against a loopback fixture server, real SQLite usage aggregation, reply parsing,
execution analytics dispatch, all four prompt classes plus denied/contextless
controls, and the static spending classifier. They use no provider credentials,
real charges or live message sends. These are not live provider billing evidence.
The fixture independently expects 35 input and 12 output tokens across two calls;
money remains unknown. Cancelled, stale and ungranted reads do not read the ledger.

Oracle review required one correction: execution instructions must limit
analytics to task-relevant questions, not every worker with availability. The
correction also makes clear that older paid-tool help cannot override no-spend.
No ordinary tests are retained. Publication, loaded revision and live inspection
are recorded separately after the corresponding checks, never inferred from code.

## Parked durable accounting

Future K4 implementation requires explicit durable-schema approval and a changed
spending policy, not guessed caps. Proposed acceptance remains: atomic competing
reservations across processes; immutable host scope/task/operation binding; only
first admission permits dispatch; repeated operation never replays; confirmed
no-charge releases; timeout/crash/unknown hold across restart; known charges
settle without being mislabeled invoices. F001/F002 are real release gates.
These reservation/settlement cases have **not** been implemented or verified by
the static denial slice, and included inference will not be put behind that ledger.
